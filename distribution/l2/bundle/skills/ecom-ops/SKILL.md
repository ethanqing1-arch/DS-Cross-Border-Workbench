# 电商数据复盘

## 什么时候用

用户要看店铺经营状况、找下滑原因、决定砍哪个品、或要一份能发出去的日报。

## 口径必须先定死（否则看板是装饰品）

| 指标 | 口径 | 常见打架 |
| --- | --- | --- |
| GMV | 下单且未取消的订单金额，按**支付时间**归日 | 下单/支付/确认收货 三个都有人叫销售额 |
| 净销售额 | GMV − 退款 − 赠品 | 财务核算与提成口径 |
| 退款率 | **退款金额 ÷ GMV**（按金额） | 按订单数算能差一倍 |
| 推广 ROI | GMV ÷ 推广花费（好看）／**贡献利润 ÷ 推广花费**（真实） | 用 GMV 口径会误判投放 |
| 客单价 | 净销售额 ÷ **成交用户数** | 除以订单数会偏低 |
| 贡献利润 | 实付 − 商品成本 − 平台扣费 − 物流 − 分摊推广费 − 退货损耗 | 用毛利率会高估 |

**检验口径是否落地的唯一标准**：随便抓两个业务人员问同一个指标定义，答案必须一致。

## 看板五模块，每块只回答一个问题

1. **整体经营**（GMV/订单/客单价/访客/转化率/退款率/推广费/ROI）→ 今天盘子怎么样
2. **平台表现**（横向对比 GMV/转化/客单价/退款率/ROI）→ 谁在拉增长，谁在拖后腿
3. **商品表现**（爆款/滞销/高毛利/高退货）→ 什么值得推，什么要调整
4. **流量转化**（访客/点击率/加购率/支付转化/广告消耗/投产比）→ 流量有没有变成成交
5. **风险预警** → 什么要马上处理

不要什么都往看板塞。五块之外的内容另开文档。

## 异常必须量化

写「波动超过 20% 算异常」，否则它永远告诉你「今天一切正常」。脚本内置阈值：

| 预警 | 阈值 | 默认动作 |
| --- | --- | --- |
| 整体退款率 | >12% | 抽查最近 10 单退货原因，比对详情页 |
| 单品退款率 | >30% | 暂停推广，先查质量/描述不符 |
| 贡献利润为负 | <0 | 核对成本与推广，两周无改善下架 |
| 单日净销售额 | 环比跌 >20% | 查渠道流量与前一日投放 |
| 待发货积压 | >2 单 | 当天 18 点前出库 |
| 库存 | <30 件 | 立即补货，暂停放量 |

## 素材与命令

所有相对路径（`data/…`、`scripts/…`、`out/…`）以**当前 Bot 的 work_dir（团队工作区根）**为基准，不是 shell 的 cwd；
Bot 没有独立 work_dir 时，用团队工作区根。

- `data/orders.csv`（日期/订单号/SKU/数量/实付金额/推广费分摊/退款金额/状态/渠道/买家ID）
- `data/products.csv`（算成本要用）
- 跑 `python3 scripts/ops_report.py --days 7`
- 产出 `out/运营日报.md`

## 执行流程

1. 确认 orders.csv 是最新的。
2. 跑脚本。
3. 按顺序读：核心指标 → 分 SKU 贡献 → 预警（逐条给动作，不要只念）。
4. 输出 3 条动作，每条带时间。

## 推广再分配（ROI 出来之后必须做）

ROI 高的渠道加预算；ROI 低的先减一半试几天，连续几天还是低就停。这是数据驱动决策最直接的体现。

## 汇报格式

日报必须四段，缺一段不算完成：

1. **一句话结论**（本期净销售额 ××，主要问题是 ××）
2. **核心指标表**（含 ROI 与真实投产两个口径）
3. **异常与归因**（每条预警跟一句可能原因）
4. **今天要做的 3 件事**（动词开头，带时间）

## 边界

- 不把估算贡献利润说成净利润；净利润还要扣推广、人工、仓储。
- 订单 <30 单要标「样本量小，趋势仅供参考」。
- 不做财务级结论，报税与成本分摊交给财务。
- 缺访客数据时明确说「无法判断转化」，不要拿订单数假装转化率。

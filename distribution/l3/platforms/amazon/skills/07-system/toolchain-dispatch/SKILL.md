# 工具链总控（能力矩阵 → 三段式调度 → 降级链）

## 何时用

- 一条取数需求不知道用哪个源，或几个源都能给但等级不同。
- 抓取报 429/403/空结果，需要按既定顺序降级而不是随手换。
- 多 skill 并发取数，需要统一限速与缓存，避免互相打爆配额。
- 新增一个数据源，需要判断它能补哪一列、证据等级上限多少。
- 季度检查凭证与配额，需要一张能对账的清单。

不归这里：写新 skill → `skill-creator`；取值之后怎么算分 → `decision-control`。

## 输入契约

| 字段 | 来源 | 缺失时怎么办 |
|---|---|---|
| `取数字段清单` | 下游 skill 的 `输入契约` | **必需**，字段名逐字用统一数据字典 |
| `精度要求` | 该字段要 A/B/C/D 哪一级 | 缺失按 B 处理，标 `[C]` 上限 |
| `时效要求` | 天级/小时级/实时 | 缺失按 7 天 TTL 处理 |
| `可用工具与凭证状态` | 环境变量 + 配额看板 | 缺失则先跑一次连通性探测，全失败 → 降级到人工 |

## 执行流程

1. **解析需求**：把下游要的字段摊平成一列，每个字段标"目标证据等级 + 时效"。输出 `取数清单.csv`（列：`field, target_grade, ttl_days, candidate_sources`）。
2. **查能力矩阵**：按 `references/capability-matrix.md` 第 1 节找该字段的候选源，按"证据等级上限 → 成本 → 速度"排序，取第一个为主源、第二三为备源。
3. **定主源与备源**：每个字段最多写 3 个源（A 源 / B 源 / C 估算），写在 `取数计划.md` 里；不许出现"多个源随便挑"。
4. **查缓存先**：按 `cache_key = sha1(tool + field + 参数)` 查 `data/cache/`，命中且未过 TTL → 直接用，并在计划里标 `cache_hit`。
5. **限速执行**：按第 4 节每工具 QPS 与并发上限发请求；用令牌桶，单工具单进程串行，跨进程用文件锁。
6. **失败分类**：401/403 → 凭证问题；429 → 限速；5xx → 服务端；空结果/字段缺失 → 数据问题；超时 → 网络。分类写进 `降级记录.md`。
7. **按链降级**：按第 4 节降级链走，每降一级把该字段的证据等级降一档（A→B→C→D），并记"降级原因 + 时间"。
8. **写回字段证据**：在候选 CSV 的 `field_evidence` 记录原始记录定位、站点、时间、数据口径、等级和与单元格一致的 `value`。有估算时保存样本与方法。缺失标「无源」/D。
9. **汇总覆盖率**：以每 SKU 固定 18 个决策字段为分母计 D，缺失和不合口径按 D。把证据交给引擎执行门禁。D >30% 封顶观察，缺证字段不得计入正式分。
10. **落盘**：三个文件写 `out/<run_id>/`，并把字段级等级交给下游。
11. **回收凭证与配额**：记录本次各工具调用数与剩余配额，写进 `取数计划.md` 尾部。
12. **月度复核**：每月核对一次"工具能力是否变化（字段缺失、限速调整、价格变动）"，变了就更新矩阵。

取数口径：同一条结论只用一个源的数；跨源数字不一致时以证据等级高者为准，并把差异写进备注，不做平均。

## 判定口径

三段式调度规则：

| 段 | 输入 | 输出 | 判定规则 |
|---|---|---|---|
| 段 1 取数需求 | 字段清单 | `取数清单.csv` | 每字段必须有 `target_grade`，没有就按 B |
| 段 2 选工具 | 清单 + 矩阵 | 主源/备源/估算源 | 证据等级优先，其次成本，最后速度 |
| 段 3 失败降级 | 错误码 | 下一源 | 每降一级，等级降一档并留痕 |

证据等级上限（写死，不许拔高）：

| 源类型 | 上限 | 说明 |
|---|---|---|
| SP-API（自家店铺） | A | 后台原始数据 |
| 卖家后台导出 | A | 广告/退货/库存报表 |
| 付费工具（卖家精灵/Sorftime/SIF） | B（销量类 C） | 工具估算不能当 A |
| 前台抓取（Firecrawl/Playwright） | B | 必须有采集时间戳 |
| 搜索 API（Tavily） | C | 只用于趋势与背景，不当销量依据 |
| 人工/经验值 | D | 必须标注 |

限速、缓存、重试：

| 项 | 口径 |
|---|---|
| SP-API | 按 endpoint 限额（订单类约 0.0167 req/s、商品类 5 req/s），令牌桶 + 429 退避 |
| 卖家精灵 / Sorftime / SIF | 每请求间隔 ≥ 2 s，单账号并发 1 |
| Firecrawl | 按套餐配额，单任务 ≤ 50 页，间隔 ≥ 1 s |
| Tavily | ≤ 10 次/分钟，单次 ≤ 400 字符查询 |
| Playwright | 自建，单域名并发 ≤ 2，间隔 3–8 s 随机，失败重试 ≤ 2 |
| 重试 | 429/5xx 指数退避 1/2/4/8 s，最多 3 次；401/403 不重试，直接换源 |
| 缓存 TTL | 搜索量 7 天；价格 1 天；评论数 3 天；BSR/库存 1 天；类目结构 30 天 |
| 缓存位置 | `data/cache/<tool>/<sha1>.json`，内含 `fetched_at`、`source`、`grade` |

降级链（按字段类型固定）：

| 字段 | A 源 | B 源 | C 估算 | D 兜底 |
|---|---|---|---|---|
| 销量/BSR | SP-API | 卖家精灵 / Sorftime | 评论增速推算 | 类目均值 |
| `monthly_search_volume` | 站内实测导出 | 同站同词 Amazon 工具导出 | 有同站校准的月搜估算 | 无源。Google Ads/lingxiao 站外量、搜索建议及未校准排名分列 |
| `competitor_count` | — | 去重后的可比在售总体 | 有定义且可追溯的同口径估算 | 无源，首屏数另存 |
| `top_review_count` | — | 同一可比总体最高评论 | 同口径工具估算 | 无源 |
| `top10_share` | 同一可比总体真实销量 | — | 同一总体销量估算 | 无源，评论分布另存 |
| `price_usd` | 自家同规格成交 | 同规格同装量可比报价中位/分位 | 有据定价估算，附同规格样本 | 无源 |
| `return_rate` | 后台报表 | — | 类目均值 | 0.08 |
| `ad_share` | 广告报表 | — | 工具估算 | 0.30 |
| `cogs_cny` | 1688 询价 | 图搜同款 | 关键词搜索 | 按同类估 |

## 输出契约

- 落盘：`out/<run_id>/取数计划.md`、`out/<run_id>/取数清单.csv`、`out/<run_id>/降级记录.md`
- `取数清单.csv` 列：`field, target_grade, actual_grade, source, cache_hit, ttl_days, fetched_at, fallback_used, note`
- `降级记录.md` 列：`field, error_code, from_source, to_source, reason, at, grade_after`
- 正文格式：先给"字段覆盖率（A/B/C/D 占比）"→ 再给主源/备源表 → 再给降级记录 → 最后给"哪些字段需要人工补"。
- 消费方：01-data 的 `amz-keyword-harvest`、`amz-listing-scrape`、`amz-review-harvest`、`web-trend-scan` 全部按本 skill 的矩阵取数（它们的 `upstream` 未回填本名，待 router 统一补齐）。

## 质检清单

- [ ] 每个字段都写了主源、备源、估算源，没有"看情况"。
- [ ] 证据等级按源类型上限给，没有把工具估算写成 A。
- [ ] 缓存先查后取，命中率写进计划。
- [ ] 429 走了退避，401/403 没重试直接换源。
- [ ] 降级记录里每条都有错误码、时间、等级变化。
- [ ] 已按字段把来源交给引擎，D >30% 或缺证的门禁已反映在决策与预算。
- [ ] 凭证只从环境变量读，没写进文件、没进 git。
- [ ] 数据可信度声明：本次采集时间 ___，FX ___，未取到的字段 ___ 个。

## 反模式

- 一个字段同时调 3 个源然后取平均。→ 错：口径不同不可平均；按等级取一个，差异写备注。
- 抓不到就手填一个"差不多"的数。→ 错：填了就是 D 级，必须标 `[D]` 并触发降档规则。
- 缓存键只用字段名。→ 错：不同关键词/ASIN 会串数据；键必须含参数哈希。
- 401 也重试 3 次。→ 错：凭证失效重试无用，直接换源并报"凭证需轮换"。
- 把 Tavily 的搜索摘要当销量依据。→ 错：搜索 API 上限 C 级，只能做背景与趋势。
